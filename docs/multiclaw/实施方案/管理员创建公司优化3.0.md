# 管理员创建公司优化 3.0（完整方案）

本文档在 2.0 基础上，增加：**一次工具调用**、**CEO 唯一化**、**实体差异化描述**，并明确**如何通过模版 + 大模型生成**保证每个实体都有对应详细描述。确认后按本方案修改代码与 admin 提示词。

---

## 0. 3.0 目标与范围

| 目标 | 说明 | 可观测结果 |
|------|------|------------|
| 一次工具调用 | 用户确认后只调用一次 `create_company` 即完成落盘 | 日志中仅出现 1 次 create_company tool_call |
| CEO 唯一 | 每个实例仅一个 CEO 实体（id=`ceo`），不出现 ceo_01 等 | `workspace/entities/` 下仅有 `ceo/` |
| 实体差异化 | 每个实体的 IDENTITY/SOUL/AGENTS 与技能配置按角色、业务真正区分 | 不同实体文件内容在职责、工具、流程上明显不同 |

2.0 中已完成的「先澄清→生成草案→用户确认→再落盘」的 SOP 保持不变；3.0 在落盘方式与内容生成上做增强。

## 1. 问题 1：简化为一次工具调用

### 1.1 现状与目标

- **现状**：admin 在用户确认后依次调用 `draft` → `confirm` → `apply`，共 3 次 tool_call。
- **目标**：用户确认已在 admin SOP 中完成，落盘阶段只需 **一次** `create_company` 调用即可完成创建。

### 1.2 实现思路

- **工具行为**：  
  - 保留 `draft` / `confirm` / `apply` 三种 action 以兼容旧流程与审计。  
  - **当且仅当** `action: "apply"` 且调用参数中携带「完整草案字段」（如 `instance_identity_md`、`ceo_identity_md`、`entities` 等与 draft 一致的全量/部分字段）时，工具内部**自动完成**：写入 draft 文件 → 标记 confirmed → 执行 apply（创建实例、写 persona、写 config）。  
  - 若 `apply` 仅带 `company_id` 且无完整草案字段，则沿用当前逻辑：要求已存在已确认的 draft，否则报错。

- **Admin SOP**：  
  - 在「用户确认」之后，admin **只调用一次**：  
    `create_company { action: "apply", company_id, preset, business_domain, agent_max, instance_identity_md, instance_soul_md, instance_agents_md, ceo_identity_md, ceo_soul_md, ceo_agents_md, entities: [...] }`  
  - 不再分步调用 draft / confirm / apply。

### 1.3 修改点

- `src/tools/create_company.rs`：在 `execute` 中处理 `Apply` 时，若参数包含完整草案字段，则先内存构造 `CompanyDraftFile`（或等价逻辑），再直接执行 `apply_to_instance`，无需先写 draft 文件再读回；为保持可审计性，可在 apply 成功后可选地写一份 draft 快照到 `company_drafts/`。
- Admin 提示词（`src/entity/mod.rs` 与 `~/.multiclaw/instances/admin/workspace/AGENTS.md`）：将「工具落盘」步骤改为「仅调用一次 create_company，action=apply，并传入草案中全部字段」。

## 2. 问题 2：CEO 唯一化（消除 ceo_01）

### 2.1 根因

- `instance_manager::instance_create` 在 preset 为 startup/enterprise 时会 **scaffold 一个 `ceo` 实体目录**（硬编码）。  
- Admin 或大模型在生成 `entities[]` 时，可能把「CEO」也作为一条实体填入（例如 id=`ceo_01` 或 role=CEO），`apply_to_instance` 会再写入 config 并 scaffold 该 id，导致出现 `ceo` 与 `ceo_01` 两个目录。

### 2.2 实现思路

- **工具侧（create_company）**：  
  - 在合并 `draft.entities` 到 `inst.entities` 时，**过滤掉** id 为 `ceo` 或与 `ceo_*` 匹配的项（或统一归一为一条：只保留 CEO 由 `ceo_identity_md`/`ceo_soul_md`/`ceo_agents_md` 描述，不再从 `entities[]` 里创建 CEO）。  
  - 即：CEO 的唯一来源是「实例创建时自带的 `ceo` 目录 + draft 的 `ceo_*_md`」；`entities[]` 只用于**员工实体**。

- **Admin SOP**：  
  - 明确约束：**entities[] 只包含非 CEO 的员工/岗位**；CEO 的职责与描述**仅**通过参数 `ceo_identity_md`、`ceo_soul_md`、`ceo_agents_md` 传入，不要将 CEO 再放入 `entities` 列表。

### 2.3 修改点

- `src/tools/create_company.rs`：在 `apply_to_instance` 中，遍历 `draft.entities` 时跳过 `id == "ceo"` 或 `id.starts_with("ceo_")`（或等价规则），不写入 config、不创建对应 entity 目录。  
- 可选：若仍希望保留「由大模型生成 CEO 描述」的能力，可在文档中说明：CEO 内容由 `ceo_identity_md` 等三个字段由大模型生成，工具只写 `ceo/` 目录，不新增其他 CEO 实体。  
- Admin 提示词：在「生成草案」与「调用 create_company」的说明中，强调「entities 仅填员工，CEO 用 ceo_identity_md / ceo_soul_md / ceo_agents_md」。

## 3. 问题 3：实体差异化描述 + 模版与发挥

### 3.1 现状

- 若 admin 在调用 `create_company` 时未为每个实体提供 `identity_md` / `soul_md` / `agents_md`，工具会回退到 `scaffold_entity_workspace(id, role)`，其内容仅随 `display_name`、`entity_id`、`role` 做简单替换，**各实体之间除名称外差异很小**，职责、技能、流程不够区分度。

### 3.2 目标

- 每个实体（含 CEO）都应具备**真正有用**的差异化描述：  
  - **IDENTITY.md**：身份、职责边界、与 CEO/其他实体的协作方式、建议使用的工具/技能。  
  - **SOUL.md**：该角色的工作重心与行为偏好（可简短）。  
  - **AGENTS.md**：每会话习惯、任务执行规范、产出格式、与 CEO 的协作规则。  
- 同时，每个实体在 config 中的 **skills（allowlist）** 应与角色匹配（如运营多用 memory/file、增长可带 web_search 等），而不是全员相同。

### 3.3 策略：模版 + 大模型发挥（推荐）

**结论：既提供结构化模版给 admin/大模型做参考，又由大模型按业务与角色自由发挥填写具体内容。**

- **模版的作用**：  
  - 规定 **结构**（章节、必填段落），避免大模型输出随意或漏项。  
  - 明确 **字段含义**（如「职责」写什么、「技能与工具」写什么），便于大模型生成可直接落盘的内容。  
  - 保证不同实体之间至少**在结构上一致**，便于后续解析或扩展。

- **大模型发挥的作用**：  
  - 根据 **公司目标、业务域、preset、岗位** 填写具体文案，使「运营」「增长」「内容策划」等在不同公司、不同业务下描述不同。  
  - 为每个实体生成 **identity_md / soul_md / agents_md** 三块内容，并通过 create_company 的 `entities[].identity_md` 等传入工具落盘。

- **落盘逻辑**：  
  - 工具侧：若某实体提供了 `identity_md` / `soul_md` / `agents_md`，**优先写入**这些内容；若某文件未提供，再按该实体的 `role` 使用**按角色区分的 fallback 模版**（见下），避免全员同一份通用模版。  
  - 这样即使大模型某次少填了某个字段，实体之间仍能通过 role 维度的 fallback 有所区分。

### 3.4 模版放置与发布策略（改为方案 A，强约束）

本方案固定采用你认可的 **方案 A**：模版作为 admin skill 的一部分，跟随代码发布，并在初始化时自动落盘到 admin workspace。

- **代码仓库中的来源（Source of Truth）**：  
  - 新增内置 skill 模版目录（示例）：`assets/skills/admin_company_designer/`（或等价路径）。  
  - 目录中至少包含：  
    - `SKILL.md`（技能说明与调用约束）  
    - `entity_identity_template.md`  
    - `entity_soul_template.md`  
    - `entity_agents_template.md`  
    - `ceo_identity_template.md` / `ceo_soul_template.md` / `ceo_agents_template.md`  
    - `instance_identity_template.md` / `instance_soul_template.md` / `instance_agents_template.md`  

- **初始化自动生成（防止开发机有、服务器没有）**：  
  - 在 admin 初始化流程中（`scaffold_admin_workspace` 或其调用链）增加 `scaffold_admin_skill_templates()`：  
    - 将上述内置 skill 文件复制到：`<cluster_root>/instances/admin/workspace/skills/admin_company_designer/`。  
    - 使用“缺失则写入，不覆盖用户已修改文件”的幂等策略。  
  - 同时在 `create_company` 执行前做一次轻量兜底检查：若 skill 目录缺失则自动补齐（同样不覆盖已存在文件）。  
  - 这样即使服务端是新环境、或历史环境缺文件，也能在初始化/首次使用时自动补全。

- **版本一致性策略**：  
  - 在 `skills/admin_company_designer/meta.toml`（或 `SKILL.md` 头部）记录 `version`。  
  - admin 启动时若检测到内置版本高于本地版本，提示“发现 skill 模版更新，可执行升级同步”；默认不覆盖用户本地改写内容，仅新增缺失文件。

- **模版内容要点（建议结构）**：  
  - **IDENTITY 模版**：  
    - 身份（名称、实体 id、角色、定位一句话）。  
    - 职责（3–5 条，具体到该角色在本实例中做什么、不做什么）。  
    - 技能与工具（列出该角色建议使用的工具名或技能名，如 file_read、file_write、memory_store、memory_recall、shell、web_search_tool 等，与当前运行时工具名一致）。  
    - 工作流程（简要步骤：每会话先做什么、接到任务后怎么做、产出如何交付）。  
  - **SOUL 模版**：  
    - 你是谁、工作重心、与团队/CEO 的协作原则；可 2–4 句话。  
  - **AGENTS 模版**：  
    - 每会话必做（读 SOUL/IDENTITY、memory_recall 等）。  
    - 任务执行规范（接收任务、执行与产出、汇报）。  
    - 与 CEO 的协作（不越权、任务边界不清时如何记录与确认）。  

  每个模版中可用占位符说明，例如：`{{role}}`、`{{entity_id}}`、`{{business_domain}}`，由大模型在生成时替换为具体值并扩展成完整段落。

- **Admin 提示词约束（强制引用 skill）**：  
  - 在 admin 的 AGENTS.md「创建公司」流程中明确写入：  
    - 创建实例时，必须先读取 `skills/admin_company_designer/SKILL.md` 与对应模版文件；  
    - 必须按该 skill 结构生成 `instance_*_md`、`ceo_*_md`、`entities[*].*_md`；  
    - 未按 skill 结构生成时，不得调用 `create_company apply`。  
  - 在「生成草案」步骤中明确要求：  
    - 为**每个**员工实体生成**不少于 50 字**的 identity_md、soul_md、agents_md；  
    - 且**不同角色之间必须在职责、技能、流程上有明显区别**，不得仅改名称。  
  - CEO 的 `ceo_identity_md`、`ceo_soul_md`、`ceo_agents_md` 同样按该 skill 的 CEO 模版生成。

### 3.5 工具侧 fallback（按角色区分）

- 当某实体**未提供** identity_md / soul_md / agents_md 时，工具在落盘时应使用**按 role 区分的默认内容**，而不是同一份通用模版。  
- 实现方式示例：  
  - 在 `create_company` 或 `entity` 模块中维护一个「role → (identity, soul, agents) 片段」的映射表（如「运营」→ 侧重执行与记录、「增长」→ 侧重检索与汇报、「设计」→ 侧重产出与格式），或根据 `preset` + `business_domain` 选择不同片段组合。  
  - 在写入实体目录时，若 `ed.identity_md` 为空则用该实体的 `role` 对应片段生成 IDENTITY.md，依此类推。  
- 这样即使某次 admin 未传满所有实体的 md，落盘结果仍能体现角色差异。

### 3.6 技能（skills）差异化

- **当前**：`entities[].skills` 若为空，config 中该实体无 skills 限制，可能用全部工具。  
- **建议**：  
  - 若 admin 在草案中为每个实体指定了 `skills`（工具名列表），则原样写入 config。  
  - 若未指定，工具侧可根据 `role` 使用**预设的 role→skills 映射**（如运营：memory_store, memory_recall, file_read, file_write；增长：同上 + web_search_tool；内容：同上 + file_edit 等），写入 config，使不同角色默认拥有不同工具子集。  
- 技能模块若尚未完全适配，仍可先在 config 的 `skills` 字段上做差异化；待技能/记忆等机制完善后，再扩展为「agent 模版 + 更智能的默认技能」不迟。

### 3.7 修改点汇总（问题 3）

- **文档/模版**：  
  - 新增并维护内置 skill 目录：`assets/skills/admin_company_designer/`，包含 SKILL 与 instance/ceo/entity 三类模板文件。  
- **Admin 提示词**：  
  - 在「生成草案」中增加：**强制按 `admin_company_designer` skill** 为每个实体（及 CEO、实例）生成差异化 identity_md/soul_md/agents_md；禁止仅改名称；未提供时工具按 role 使用默认片段。  
- **工具**：  
  - 在 `apply_to_instance` 中，对实体若缺少 identity_md/soul_md/agents_md，则根据该实体的 `role`（及可选 preset、business_domain）生成 fallback 内容并写入，而不是统一用当前 `scaffold_entity_workspace` 的通用模版。  
  - 可选：为 `entities[].skills` 增加 role→skills 默认映射，在未指定时写入 config。
- **初始化链路**：  
  - 在 admin 初始化时自动将 `assets/skills/admin_company_designer/` 同步到 `instances/admin/workspace/skills/admin_company_designer/`（缺失补齐、不覆盖）。  
  - 在 `create_company` 执行前增加 skill 存在性兜底补齐，避免线上缺文件。

## 4. 实施清单（按执行顺序）

| 序号 | 项 | 说明 |
|------|----|------|
| 1 | create_company：一次 apply 完成落盘 | 当 apply 带完整草案字段时，内部完成 draft+confirm+apply，只暴露一次调用。 |
| 2 | create_company：CEO 唯一化 | 过滤 entities 中 id=ceo 或 ceo_*，不写入 config、不建目录；CEO 仅来自 ceo_*_md。 |
| 3 | 内置 Skill 资产入库 | 新增 `assets/skills/admin_company_designer/`，将模板随代码发布。 |

| 5 | Admin 提示词：强制引用 Skill | 更新 AGENTS/IDENTITY：创建公司前必须读取该 skill，按其结构生成内容后才允许 apply。 |
| 6 | Admin 提示词：一次调用 + CEO 不入 entities | 确认后只调一次 apply，entities 仅员工，CEO 用 ceo_*_md。 |
| 7 | create_company：实体 fallback | 实体缺 identity_md/soul_md/agents_md 时，按 role（及可选 preset/domain）生成差异化 fallback 并写入。 |
| 8 | create_company：skills 默认映射 | 实体未提供 skills 时，按 role 写入预设的 skills 列表到 config。 |
| 9 | 测试与回归 | 单测：一次 apply 带全参可创建成功；entities 含 ceo/ceo_01 时仅保留 ceo；实体落盘内容因 role 不同而不同；admin skill 能自动补齐。 |

## 5. 验证标准

- **一次调用**：用户确认后，仅出现 1 次 `create_company` tool_call，且实例与 persona 均正确落盘。  
- **CEO 唯一**：新实例下 `workspace/entities/` 仅存在 `ceo/`，无 `ceo_01` 等。  
- **实体差异化**：  
  - 不同 role 的实体，IDENTITY.md 中「职责」「技能与工具」段落明显不同。  
  - 若提供了 identity_md/soul_md/agents_md，落盘内容与之一致；若未提供，则 fallback 内容按 role 区分。  
- **技能**：config 中不同实体的 `skills`（若有）随角色不同而不同。
- **Skill 可用性**：新环境初始化后，`instances/admin/workspace/skills/admin_company_designer/` 必定存在且包含 SKILL 与模板文件；缺失时可自动补齐。
- **流程约束**：admin 在创建公司时会先引用 `admin_company_designer` skill，再调用 `create_company apply`，不会跳过 skill 直接落盘。

## 6. 与 2.0 的衔接

- 2.0 的「需求澄清 → 生成草案 → 用户确认 → 工具落盘」流程**不变**。  
- 3.0 仅变更：  
  - 落盘阶段从「draft → confirm → apply」改为「一次 apply 带全参」；  
  - 工具与 SOP 保证 CEO 唯一、实体描述与技能差异化；  
  - 通过「模版 + 大模型发挥」保证每个实体都有可用的详细描述，并由工具侧 fallback 兜底。
