# 管理员创建公司优化 5.0（统一创建链路与 Persona 分工）

本文档解决一个核心问题：**同一类“创建”在多个入口（admin/CEO/CLI/tool）下走了不同逻辑与不同模板来源**，导致：
- 注册表字段不一致（`team_id`/`skills`/`role` 缺失或风格分裂）
- Persona 文件不一致（有的“角色定义强但工作规范弱”，有的“工作规范强但角色定义弱”）
- 模板来源不可控（skill 模板 vs `src/entity/mod.rs` 硬编码 scaffold），环境间可重复性差

目标是：**无论从哪个入口创建实例/CEO/实体，最终落盘结果遵循同一套协议、同一套模板与同一套覆盖优先级。**

---

## 1. 问题复盘（基于当前实现）

### 1.1 多入口、多套逻辑导致结果不可控

当前至少存在这些创建入口：
- **admin 创建公司**：`create_company action=apply`，主要依赖 `admin_company_designer` 生成 payload（instance/CEO/entities 的 markdown + registry 字段）。
- **CEO 创建实体/团队**：`create_entity` / `create_team`（CEO-only tools），会调用 `scaffold_entity_workspace`，默认产出来自 `src/entity/mod.rs` 的 scaffold 文案；也可能再由 CEO 用 `file_write` 补写 persona。
- **CLI/instance_manager**：`instance_create` 在某些 preset 下会 scaffold CEO。

这些入口在“最终输出结构、模板来源、覆盖逻辑”上并不统一，导致你在 `.docs/团队创建问题.md` 中观察到的差异：
- admin 创建的实体：`IDENTITY.md` 更像“角色定义”，但 `AGENTS.md` 模板过于通用且容易所有实体相同。
- CEO 创建的实体：`AGENTS.md`/流程规范更标准，但 `IDENTITY.md` 容易变成“通用执行单元描述”，角色差异弱。
- 注册表字段：有的只有 `team_id/role`，有的只有 `role/skills`，缺乏“最小完整信息”的统一约束。

### 1.2 当前模板/写入来源（事实链路）

**A) 代码硬编码 scaffold（`src/entity/mod.rs`）**
- `scaffold_entity_workspace()` 会在文件不存在时写入 `IDENTITY.md/SOUL.md/AGENTS.md`（idempotent，不覆盖）。
- 当是 CEO 时，还会下发 `skills/ceo_entity_designer/*`（同样是缺失才写）。

**B) admin/CEO 的 skill 模板（`assets/skills/**`）**
- `admin_company_designer`：作为草案生成参考；只有当 admin 把内容塞进 `create_company` 的 payload，才会真正覆盖到目标实例。
- `ceo_entity_designer`：作为 CEO 侧“从意图->参数->一次性 create_entity 写入 persona”的流程规范与模板来源。

**C) tool 覆盖写入（强覆盖）**
- `create_company`：会 scaffold CEO 工作区后，再用 `ceo_*_md` 覆盖 CEO 的 3 个 persona 文件（只要 payload 提供）。
- `create_entity`（CEO tool）：会 scaffold 后，再用 `identity_md/soul_md/agents_md` 覆盖对应文件（只要参数提供）。

## 2. 5.0 目标（统一协议）

### 2.1 统一创建逻辑（多入口同结果）
- 不管入口是 **admin / CEO / CLI**，最终落盘应一致：
  - **注册表字段**（config.toml/instances.json）遵循统一最小集与默认策略
  - **Persona 文件职责分工一致**
  - **模板来源单一且可追溯**

### 2.2 Persona 分工明确（“规范”与“角色”拆分）
为解决“角色定义强但规范弱 / 规范强但角色弱”的互补问题，5.0 采用固定分工：

- **`AGENTS.md`：实例级统一的“工作规范/运行规约”**
  - 必须包含：读 SOUL/IDENTITY、memory_recall、产出记录、与 CEO 汇报、跨实体协作边界、文件路径与可审计输出要求。
  - 允许包含：本角色推荐工具使用规则（但不承担角色职责描述的主表达）。

- **`IDENTITY.md`：强角色定位 + 可执行的职责与工作流程**
  - 必须包含：角色定位（role/team/company/entity_id）、职责边界（做什么/不做什么）、典型交付物、与上下游的接口约定、关键工作流程（更贴近该岗位）。
  - 不应退化为通用“执行单元描述”。

- **`SOUL.md`：价值观/行为风格（轻量、稳定）**
  - 简短即可：做事原则、遇到不确定先澄清、保持可追溯交付。

> 备注：你提到“每个实体都有 agent.md/Identity.md”，在当前工程里 canonical 文件名是 `AGENTS.md`。5.0 方案统一以 `AGENTS.md` 为准，不引入新文件名以避免兼容与迁移成本。

### 2.3 注册表字段最小完整集（统一约束）

对每个 `[[instance.entities]]`，5.0 统一要求：
- **必填**：`id`
- **强烈建议**：`role`
- **可选但规范化**：
  - `team_id`：建议默认填充为 `"core"` 或 `"unassigned"`（由创建流程决定）
  - `skills`：若未提供则由 role-based 默认映射补齐；若提供则必须是允许的 tool/skill 名称（避免“业务技能名”与“工具技能名”混用）

> 当前问题里出现的 `skills = ["market_research", ...]` 很可能是“业务能力名”而不是系统工具/skill 名。5.0 需要明确区分：
> - **工具/系统能力 allowlist**：影响 tool 暴露（如 `file_read`, `memory_recall`）
> - **岗位能力标签**：用于描述，不应写入 allowlist 字段（否则导致工具过滤异常）

## 3. 方案总览（统一到“单一真源模板 + 统一覆盖优先级”）

### 3.1 单一真源：把“可控模板”变成唯一来源

5.0 建议将 persona 生成模板分成两类，并统一放在代码资产里（`assets/skills/`），由运行时下发：

1) **公司创建模板（admin 用）**：`assets/skills/admin_company_designer/`
- 用于生成 instance/CEO/employee 的三层 persona 与实体草案

2) **实体创建模板（CEO 用）**：`assets/skills/ceo_entity_designer/`
- 用于把“创建岗位/成员/团队”的意图，稳定转成：
  - `create_team`（可选）
  - `create_entity`（一次性携带 persona）

并明确：**`src/entity/mod.rs` 的 scaffold 只作为兜底（fallback），不能成为主要创作来源**。

### 3.2 覆盖优先级统一（所有入口一致）

统一优先级（从高到低）：
1. **工具入参显式 persona**（admin: `ceo_*_md` / `entities[].*_md`；CEO: `identity_md/soul_md/agents_md`）
2. **工作区已有文件**（认为是用户/上一次生成结果，默认不覆盖）
3. **scaffold fallback**（缺失才写）

这一条要对所有入口成立，避免“有时覆盖、有时不覆盖”的漂移。

### 3.3 创建流程统一：谁负责生成 persona？

5.0 统一责任：
- **创建公司（admin）**：必须生成并传入所有 persona（instance + CEO + entities）。不再依赖 `mod.rs` 默认文案作为主产物。
- **创建实体（CEO）**：必须尽量在 `create_entity` 单次调用中传入 persona（三件套），避免“create_entity + 多次 file_write”。
- **CLI 创建（instance_create）**：只做最小 scaffold（为可用性），但鼓励后续通过 admin/CEO 流程补齐高质量 persona。

## 4. 需要改造的点（对应当前代码与行为）

### 4.1 统一注册表字段写入

**问题现状：**
- admin 侧 `create_company` 会写 `team_id/role/skills`（但 skills 可能为空或随模板漂移）
- CEO 侧 `create_entity` 允许只写 `role`，`team_id/skills` 由交互决定，且 skills 可能写入非工具 allowlist 的“业务技能名”

**5.0 改造建议：**
- 将 `skills` 字段语义收敛为“工具 allowlist”，并提供：
  - role-based 默认 allowlist（仅当未提供时补齐）
  - 对明显的“业务技能名”进行校验/拒绝/自动迁移到 persona 文案（不写入 allowlist）
- 对 `team_id`：
  - 若未提供，写入一个明确的默认值（如 `"core"` 或 `"unassigned"`），并在 persona 中体现“未分配团队”

### 4.2 统一 persona 模板：让 AGENTS 真正体现“标准工作规范”

**问题现状：**
- `admin_company_designer/entity_agents_template.md` 过于通用（导致所有实体 AGENTS 相同）
- `mod.rs` 的 entity scaffold 有标准流程，但角色差异弱

**5.0 改造建议：**
- 固化一份“全员通用工作规范”写入 `AGENTS.md`（可在模板中引用固定段落），包含：
  - 会话 checklist：读 IDENTITY/SOUL、memory_recall、确认产出、记录结果
  - 协作边界：向 CEO 汇报、禁止越权、输入输出契约
  - 可审计输出：结论+依据+路径+下一步
- `IDENTITY.md` 则必须包含岗位差异化内容（职责/交付物/流程/接口），并在创建流程中强制生成 3 条“真实职责”而不是占位符。

### 4.3 统一“入口行为”：admin/CEO 都走同一套创作 SOP

**5.0 改造建议：**
- admin：继续强制 `admin_company_designer`，但补充一个“persona 分工与质量门槛”的 checklist（禁止占位符、禁止同质化 AGENTS）。
- CEO：强制 `ceo_entity_designer`，并明确：
  - “角色/岗位/员工/成员/招人” -> 创建实体
  - “团队/小组/部门” -> 创建团队
  - 最终只允许一次 `create_entity` 完成 persona 落盘（除非用户要求后续手改）

## 5. 分阶段实施计划（建议）

### P1：定义统一契约（低风险）
- 明确 `skills` 字段语义：工具 allowlist；业务能力写入 persona，不写入 allowlist
- 明确 `team_id` 默认策略
- 明确 persona 分工：AGENTS=规范，IDENTITY=角色，SOUL=风格

### P2：模板统一（中风险，效果最大）
- 更新 `assets/skills/admin_company_designer/entity_agents_template.md`：
  - 写入统一工作规范段落（会话 checklist + 协作边界 + 可审计输出）
- 更新 `assets/skills/admin_company_designer/entity_identity_template.md`：
  - 强制包含“角色专属工作流程/交付物/边界”
- 更新 `assets/skills/ceo_entity_designer/*` 同步同样分工

### P3：工具与校验收敛（中风险）
- `create_entity`：
  - 对 `skills` 做校验（拒绝明显的业务技能名或提示修正）
  - 为缺失字段补默认（team_id、skills）
- `create_company`：
  - 在执行前做 payload 完整性检查（entities 的三件套、CEO 三件套、team_id/role/skills 规范）

### P4：迁移与一致性修复（可选）
- 提供一个“修复器”（doctor 子命令或工具）：
  - 扫描实例下 entity 的 persona 是否缺失/同质化
  - 扫描 config entities 是否缺少 team_id/skills
  - 以“只补缺失、不覆盖用户手改”为原则修复

## 6. 验收标准（必须可观测）

### 6.1 多入口一致性
- 同一个角色（例如 `product-manager`）分别通过：
  - admin create_company（在公司创建时就生成）
  - CEO create_entity（后续增员）
  产出的：
  - config 注册字段（id/role/team_id/skills）风格一致、字段齐全
  - `IDENTITY.md` 体现角色职责与流程，非通用文案
  - `AGENTS.md` 体现统一工作规范，且不应因入口不同而缺失关键流程

### 6.2 persona 分工有效
- `AGENTS.md`：包含统一 checklist + memory + 协作边界 + 可审计输出
- `IDENTITY.md`：包含角色定位、职责边界、典型交付物、岗位流程
- `SOUL.md`：轻量且稳定

### 6.3 skills 字段语义正确
- `[[instance.entities]].skills` 仅包含系统工具/skill allowlist（不会出现 `market_research` 这类业务能力名）
- 业务能力应体现在 `IDENTITY.md`/`AGENTS.md` 的描述，而不是 allowlist 字段

## 7. 风险与回滚

### 风险
- 收敛 `skills` 语义会影响“工具过滤”行为（若历史数据写了业务技能名，可能导致工具暴露异常）
- 模板统一会影响生成结果，需要校验避免过度同质化

### 缓解
- 只对“新创建”强制；对存量实例提供修复器，且默认只补缺失不覆盖
- 对 `skills` 加迁移策略：发现业务技能名时给出明确报错与建议修正路径

### 回滚
- 回滚模板与校验逻辑即可恢复旧行为（不动用户已生成文件）
