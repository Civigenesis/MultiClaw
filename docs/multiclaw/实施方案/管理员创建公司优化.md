# 管理员（Admin/董事长）创建公司流程优化方案

> 目标：修复“创建公司在 CLI/Web 下不可用/不可执行”的问题，并将创建公司从“模板脚手架”升级为“严格 1-6 步、可审计、可确认、可落盘”的产品级流程。
>
> 来源问题：见 `/.docs/团队创建问题.md`（L5-L92）。
>
> 最后更新：2026-03-18

---

## 一、现状与问题复盘（症状）

### 1.1 CLI 对话：用户说“创建公司”，Agent 却去配置 delegate agent

复现输入（摘录）：
- “帮我创建一家公司，作为我的个人助理… 最大 agent 数量 10 个，中等资源…”

实际行为（摘录）：
- Agent 认为这是“delegate agent / model routing”问题
- 调用 `model_routing_config upsert_agent`，并把“最大 agent 数量=10”误映射到 `max_iterations`

用户感知：
- “创建公司”的业务意图没有被满足
- 还出现了工具参数不匹配（temperature）等二次问题

### 1.2 Web 控制台对话：只展示 tool_call，没有实际执行

复现片段（摘录）：
- 输出 `<tool_call><function=shell>multiclaw instance list</function></tool_call>`
- 但没有真正执行，也没有 tool_result

用户感知：
- “网关创建公司完全不可用”
- “只看到命令调用，没有实际执行”

### 1.3 创建公司使用模板，不利用大模型智能

现有 `instance create` 做的是基础设施脚手架：
- 创建目录、写最小 config、生成通用模板 persona
- 不会根据“新媒体运营公司/个人助理公司”等具体需求生成公司章程、组织架构、CEO 职责、资源约束

### 1.4 Agent 对话模式：已确认出现“授权/安全策略”导致 CLI 命令无法执行

最新复现（摘录）：
- Agent 尝试执行：`multiclaw --instance admin instance create newmedia --preset startup`
- 用户在 CLI 审批提示中选择 `y`
- 随后 Agent 反馈：“`multiclaw` CLI 命令需要安全策略授权才能执行”，并改用 `curl` 访问不存在的网关端点（例如 `POST http://localhost:8080/api/admin/instance/create`）

用户感知：
- 即使批准了 `shell`，仍无法完成创建
- Agent 会“自发猜测”不存在的 API/端口，进一步增加混乱

## 二、根因诊断（原因）

### 2.1 Web 控制台“只展示 tool_call”根因：WebSocket 聊天不执行工具

当前 `src/gateway/ws.rs` 的 WebSocket 聊天实现是**单轮纯文本**：
- 仅调用 `provider.chat_with_system(...)`
- 注释中明确：`Simple single-turn chat (no streaming for now — use provider.chat_with_system)`

结论：
- 模型生成的 `<tool_call>` 只是文本，网关不会解析/调度工具
- 因此 Web 控制台必然“只展示调用、不执行”

### 2.2 CLI “创建公司”误走 `model_routing_config` 根因：缺少一体化能力入口 + 意图歧义

当前系统对“创建公司”存在两种可能解释：
- 解释 A：创建一个 **实例（公司）**（cluster instance）
- 解释 B：创建一个 **代理/子 agent**（delegate agent）

由于缺少：
- 明确的“创建公司”工具（`create_company`）
- 明确的 1-6 步 SOP（采集细节→生成草案→用户确认→再落盘）

模型只能在现有工具里“猜”，而“个人助理 + 最大 agent 数量 10”触发了它对 delegate agent 的联想，导致误用 `model_routing_config`。

### 2.3 “权限/审批”在 Web 场景不可落地

当前审批系统（`src/approval/mod.rs`）的交互形态是 CLI stdin，且代码中有注释/假设：
- approval “only supported on CLI for now”

结论：
- 即便 Web 侧未来执行工具，遇到需要审批的工具（例如 `shell`/`file_write`）也会卡住或退化为“无法执行”。

### 2.4 Agent 对话模式的“授权问题”根因：`shell` 命令白名单不包含 `multiclaw`

当前默认安全策略为 `autonomy.level = supervised`，并且对 `shell` 执行有两层门槛：
- **交互审批**（用户在 CLI 中选择 Y/N/A）
- **命令白名单**（`[autonomy].allowed_commands`）

在 admin 实例的默认配置中，`allowed_commands` 通常只包含 `git/npm/cargo/ls/...`，**不包含 `multiclaw`**。

因此表现为：
- 你在 CLI 里按了 `y` 仅代表“同意本次工具调用”，但仍会被命令白名单拦截；
- Agent 误以为是“需要额外授权/策略”，转而尝试构造 HTTP API，但：
  - admin 实例的网关端口并非 8080（当前默认是 42617）；
  - 也不存在 `/api/admin/instance/create` 这样的端点（目前只有 `multiclaw instance create` CLI、以及 `POST /api/admin-message` 这类消息投递端点）。

短期结论：
- **只要继续依赖 `shell` 跑 `multiclaw` CLI，就必须把 `multiclaw` 加入 admin 的 `allowed_commands`**。
中期结论：
- 用 `create_company` Tool 直接在 Rust 内部调用 `instance_manager::instance_create` 可以彻底绕开 `shell` 白名单与审批摩擦（更安全、更可审计）。

## 三、目标形态（严格 1-6 步创建公司）

你提出的理想流程（确认正确）：

1. 用户说要创建一家公司（公司类型/用途）
2. 董事长询问公司细节（目标、初步架构、资源限制、风格、合规边界）
3. 用户返回细节
4. 董事长生成“公司说明、CEO 说明、必备实体岗位建议、资源约束草案”
5. 用户确认无误（审批点）
6. 董事长调用工具创建公司并落盘（实例目录 + 配置 + persona + 实体）

该流程的关键价值：
- **可审计**：创建前所有假设/约束落为文件草案
- **可控**：用户确认后再执行不可逆落盘动作
- **可扩展**：后续可接预算/额度分配与审批工单

## 四、完整优化方案（工程落地）

本方案分为三条主线，同时推进：
- A) 新增 `create_company` 工具：把“创建公司”产品化（强推荐）
- B) 修复 Web 控制台：让工具调用可执行、可回传、可审批
- C) 约束与配置：明确 `agent_max` 等资源限制的语义与落盘位置

### 4.1 主线 A：新增 `create_company` Tool（推荐方案 1）

#### 4.1.1 工具职责
新增 Rust Tool：`create_company`

核心职责：
- 严格执行 1-6 步（内部维护状态机 / 草案文件）
- 产出公司资产（公司章程、CEO 说明、初始岗位实体）
- 最后调用 `instance_manager::instance_create` 完成实例落盘
- 追加写入：覆盖/补全新实例的 workspace persona 与 CEO/entity persona（不再停留模板）

#### 4.1.2 参数与输出（建议）
输入参数（最小必要）：
- `company_id`：实例 id（用于目录名）
- `company_name`：展示名（写入公司说明与 identity）
- `business_domain`：行业/场景（如“新媒体运营”“个人助理”）
- `goals`：目标（可多条）
- `initial_structure`：初步组织结构（可选；缺省由模型建议）
- `constraints`：资源限制（必须支持 `agent_max`；可扩展预算/调用额度）
- `preset`：实例 preset（建议统一语义，见 4.3）
- `mode`：`draft | confirm | apply`

输出：
- `draft_id`（草案编号）
- 草案摘要（供用户审批）
- apply 后返回：实例端口、workspace 路径、已创建实体列表

#### 4.1.3 草案存储（可审计）
建议草案文件落盘在 admin workspace：
- `~/.multiclaw/instances/admin/workspace/state/company_drafts/<company_id>.json`
- `.../<company_id>.md`（人类可读摘要）

草案必须包含：
- 用户输入原文/关键信息
- 模型生成的公司说明/CEO 说明/岗位列表
- 资源限制（agent_max 等）
- 待审批项（Yes/No）

#### 4.1.4 权限与安全
- 仅 admin 实例允许执行 `create_company`
- `apply` 阶段属于高风险写盘，应走审批 gating（Web/CLI 均可）
- 任何涉及 `shell` 的执行都应被替代为内部 Rust 逻辑（避免 `shell` 风险）

#### 4.1.5 与现有代码的复用点
复用：
- `instance_manager::instance_create`（目录/端口/注册表）
- `entity::scaffold_instance_workspace` / `scaffold_entity_workspace`

增强：
- 在创建后用 `file_write`（或直接 tokio fs）写入更详细的：
  - 实例层 `IDENTITY/SOUL/AGENTS`（公司章程式）
  - CEO `IDENTITY/AGENTS`（运营/编排职责）
  - 运营/研发/数据等实体 `IDENTITY/AGENTS`（职责+工作流+skills allowlist）

---

### 4.2 主线 B：修复 Web 控制台工具执行（让“展示 tool_call”变为“真的跑”）

#### 4.2.1 目标行为
WebSocket 协议应支持：
- 服务端发送 `tool_call`（结构化）
- 服务端执行工具并发送 `tool_result`
- 最终发送 `done`

#### 4.2.2 当前缺陷
`src/gateway/ws.rs` 只做单轮聊天，不执行工具。

#### 4.2.3 修复建议（两步走）
**阶段 1（最小修复）**：
- WebSocket chat 直接复用 `run_gateway_chat_with_tools()` 的 tool-loop（在 `src/gateway/mod.rs` 已存在）
- 先不做 streaming，至少确保 tool 能执行并把最终 response 返回

**阶段 2（体验修复）**：
- 在 tool-loop 中向 WS 发送事件：
  - `tool_call`（name/args）
  - `tool_result`（success/output/error）
  - `chunk`（可选）
  - `done`

#### 4.2.4 Web 审批（必须补）
由于 approval 目前“只支持 CLI stdin”，Web 必须实现一种替代：
- 方案 A：Web 控制台提供“approve/reject” API（SSE/WS 事件驱动）
- 方案 B：Web 环境默认只允许低风险工具（read-only），高风险工具统一拒绝并返回“需要在 CLI 批准/执行”

建议：
- 对“创建公司”这种高价值流程，走 `create_company` Tool（内部 Rust 落盘）可显著降低对 `shell` 审批的依赖。

---

### 4.3 主线 C：资源限制与 preset 语义收敛

#### 4.3.1 `agent_max` 的语义
用户表达“最大 agent 数量 10”应落到：
- 实例 registry 的 `constraints.agent_max = 10`

并在运行时注入：
- CEO 创建实体时限制（当前已支持从 registry 注入 agent_max 到 CEO 工具）

同时明确：
- 这不是 delegate agent 的 `max_iterations`
- UI/文档里应叫“实例实体上限（agent_max）”

#### 4.3.2 preset 的现状与问题
当前 `instance_manager` 里只有 `startup/enterprise` 触发 CEO scaffold 与 `[instance]` 写入，其他 preset 主要是标记。

建议收敛：
- **公司型 preset**：默认启用 CEO（并生成 CEO workspace），允许多实体协作
- **轻量 preset**（如自由对话/一次性 brainstorm）：可不启用 CEO

并在 `create_company` 工具里把 preset 当作：
- “默认组织结构/岗位包 + 默认工具白名单 + 默认汇报节奏”的策略入口

## 六、验收标准（Definition of Done）

1. CLI：对 admin 说“创建公司 + agent_max”等，系统走 1-6 流程，不再误用 `model_routing_config`
2. Web：工具调用可执行并返回 tool_result，不再只展示 `<tool_call>` 文本
3. 创建出的公司实例具备：
   - 详细公司说明（实例层 persona 或 COMPANY.md）
   - 详细 CEO 说明（CEO persona）
   - 必备实体（如运营/研发/数据等，按模型建议与 preset 策略生成）
   - `constraints.agent_max` 生效（CEO 创建实体受限）
4. 整个流程可审计：草案与确认记录可回溯
