# 管理员创建公司优化 4.0（方案草案）

本文档针对当前新增的三类问题给出**先方案、后实施**的改造设计。  
范围聚焦于你在 `.docs/团队创建问题.md` 中 98-158 行反馈的两点：

1. 新创建实例缺少默认模型配置，导致 CEO 对话直接报错  
2. CEO 创建员工/团队缺少标准化流程，意图识别与落盘行为不稳定
3. admin 创建公司仍触发 `draft -> confirm -> apply` 三次工具调用，而 4.0 目标是“工具层只保留单步 apply”

---

## 0. 问题复盘（基于现状日志）

### 0.1 问题 A：新实例模型配置缺失

现象：
- 执行 `multiclaw agent --instance newmedia_regression_0319c --entity ceo -m "你是谁"` 报错：
  - `Error: default_provider is not set...`

影响：
- 新实例虽然创建成功，但 CEO 无法直接启动会话，必须额外手动补配置。
- 破坏了“创建即可用”体验。

根因（代码侧）：
- `instance_manager::minimal_instance_config()` 目前没有写入 `default_provider/default_model`；
- `create_company` 也未强制在新实例 `config.toml` 中补齐模型主配置。

---

### 0.2 问题 B：CEO 创建实体流程不标准

现象：
- 「帮我新建一个商业产品经理角色」被 CEO 误解为“做商业分析”而不是创建实体；
- 「帮我创建一个创业策划的员工」虽能走 `create_entity`，但后续又出现多次 `file_write` 路径纠错（绝对路径被策略拒绝 -> 再改相对路径）；
- 无统一 SOP，易出现多余工具调用与流程漂移。

影响：
- 用户表达“角色/岗位/员工”时行为不一致；
- 工具调用次数偏高，交互冗长；
- 人工审批负担上升。

根因（设计侧）：
- CEO 侧缺少与 admin 类似的“技能 + 提示词强约束”；
- `create_entity` 工具本身已能落盘，但缺少“从意图到参数”的标准化中间层；
- 提示词未明确“角色=实体创建请求”的归一化规则。

---

### 0.3 问题 C：公司创建仍是三次工具调用（需硬切换）

现象（你提供的 301-852 行日志）：
- admin 在用户确认后，先尝试 `create_company action=apply`
- 但模型/工具返回“需要先 draft/confirm”，随后又执行：
  - `create_company action=draft`
  - `create_company action=confirm`
  - 再次 `create_company action=apply`

影响：
- 与 3.0 设计目标冲突（确认前置后应单次落盘）；
- 工具调用次数增加，审批次数增加，流程变长；
- 用户容易误判“还没创建成功”。

根因：
- 工具协议仍保留 `draft/confirm`，模型会继续选择旧路径；
- 提示词与工具协议存在“双轨”导致回退概率高；
- 缺少“协议级删除旧动作”的硬约束。

---

## 1. 4.0 目标

### 1.1 创建即可用（模型配置）
- 任意通过 `create_company` 或 `instance_create` 创建的实例，都应具备可用的 `default_provider/default_model`。
- 直接对 CEO 对话不再因模型配置缺失失败。

### 1.2 CEO 实体创建标准化
- 用户表达「创建角色/岗位/员工/成员」时，CEO 都能稳定识别为创建实体请求。
- CEO 侧形成固定 SOP：澄清 -> 草案 -> 确认 -> 单次工具执行。
- 减少无效 `file_write` 与路径错误重试。

### 1.3 公司创建单次调用化（admin）
- 用户确认后，admin 仅允许一次 `create_company action=apply` 调用完成创建。
- 在工具层直接删除 `action=draft`、`action=confirm`，只保留 `action=apply`。

---

## 2. 改造方案总览

## 2.1 方案 A：实例模型配置继承与补齐（必须做）

### 设计原则
- 优先使用**来源明确且稳定**的默认模型配置；
- 不引入破坏性迁移，不改变现有用户显式配置优先级。

### 继承优先级（创建新实例时）
1. 显式传入（如后续扩展 create_company 参数）  
2. 当前 admin 实例配置（`instances/admin/config.toml`）的 `default_provider/default_model`  
3. 集群根配置（`~/.multiclaw/config.toml`）  
4. 内置 provider 默认模型映射（`onboard::default_model_for_provider` 对应策略）

### 落点
- 在实例创建路径统一补齐（推荐在 `instance_manager::instance_create` + `create_company::apply_to_instance` 双保险）：
  - 若 `default_provider` 为空 -> 按优先级填充；
  - 若 `default_model` 为空 -> 基于 provider 填充；
  - 仅在字段缺失时写入，不覆盖已有值。

### 兼容性
- 对已有实例不强制改写；
- 新实例默认“可立即对话”。

---

## 2.2 方案 B：公司创建单次调用化（admin，必须做）

### B1. 工具协议硬切换（删除旧动作）
- `CreateCompanyAction` 仅保留 `Apply`。
- 删除 `Draft` / `Confirm` 相关枚举、分支、提示文案、测试用例。
- `parameters_schema` 的 `action.enum` 仅允许 `["apply"]`。
- 工具说明统一改为“single-step apply only”。

### B2. 提示词与技能统一
- admin 的 `AGENTS.md` 与 `skills/admin_company_designer/SKILL.md` 中统一写明：
  - 用户确认后，只调用一次 `create_company action=apply`
  - 协议层已移除 `draft/confirm`，不允许再出现相关调用
- 删除所有“Next: confirm then apply”类旧文案，避免模型回退。

### B3. 错误处理策略
- 若 `action=apply` 失败：
  - 首先复述错误并请求用户确认是否重试；
- 不自动降级为任何“草稿/确认”子流程；
- 仅允许“修正 payload 后再次 apply”。

---

## 2.3 方案 C：CEO 创建实体标准化（必须做）

### C1. 新增 CEO 技能（与 admin 同范式）

新增内置 skill（建议）：
- `assets/skills/ceo_entity_designer/`
  - `SKILL.md`
  - `entity_identity_template.md`
  - `entity_soul_template.md`
  - `entity_agents_template.md`
  - `team_template.md`（可选）

初始化同步：
- 在 CEO 工作区初始化时自动落盘到：  
  - `instances/<id>/workspace/entities/ceo/skills/ceo_entity_designer/`
- 策略：缺失补齐，不覆盖用户手改内容。

---

### C2. CEO 提示词/SOP 强约束

在 CEO 的 `AGENTS.md` 增加硬规则：
- 语义归一：
  - “角色/岗位/员工/成员/招人” -> 统一视为创建实体意图；
  - “团队/组/部门” -> 统一视为创建团队意图。
- 流程约束：
  1) 先确认最小字段（id、role、team_id 可选、skills 可选）  
  2) 按 `ceo_entity_designer` 生成实体草案（identity/soul/agents）  
  3) 用户确认后，调用 `create_entity`（团队不存在则先 `create_team`）  
  4) 创建后只做必要补充，不重复写无效路径
- 路径约束：
  - `file_write` 必须使用 workspace 相对路径（禁止绝对路径）。

---

### C3. 工具层收敛（减少额外 file_write）

当前 `create_entity` 已会 scaffold 默认 persona。4.0 建议增强为：
- `create_entity` 支持可选参数：
  - `identity_md` / `soul_md` / `agents_md`
- 若传入，工具内直接落盘对应文件；
- 若未传入，则走 role-based fallback scaffold（保留现逻辑）。

收益：
- CEO 不需要“先 create_entity 再多轮 file_write 补文案”；
- 减少工具调用与路径错误。

---

## 3. 分阶段实施计划

## P1（高优先，先保可用）
1. 实例创建补齐 `default_provider/default_model`（方案 A）  
2. 新增回归测试：新实例 `--entity ceo` 首次对话不报模型缺失  

## P2（高优先，流程收敛）
1. 收敛公司创建到单次 `action=apply`（方案 B）  
2. **删除** `draft/confirm` 代码与测试，完成协议硬切换  
3. 更新 admin skill/提示词，移除所有三步调用表达  
3. 增加 `ceo_entity_designer` 技能资产与自动落盘  
4. 更新 CEO 提示词：角色/员工/岗位意图归一 + SOP 强约束  

## P3（中优先，工具体验优化）
1. 扩展 `create_entity` 接收 `*_md` 参数并直接落盘  
2. 减少二次 `file_write`，降低审批次数与路径错误率  

---

## 4. 验收标准（必须可观测）

### 4.1 模型配置验收
- 新建实例后直接执行：
  - `multiclaw agent --instance <id> --entity ceo -m "你是谁"`
- 期望：
  - 不出现 `default_provider is not set` 报错；
  - CEO 会话正常响应。

### 4.2 CEO 意图识别验收
- 输入：
  - “帮我新建一个商业产品经理角色”
  - “帮我创建一个创业策划的员工”
- 期望：
  - 两者都进入“创建实体”流程（而非商业分析流程）；
  - 工具调用以 `create_entity` 为主，不出现多轮无效路径 file_write。

### 4.3 公司创建单次调用验收（新增）
- 输入：按你给的案例（ai-product-lab）走“澄清->草案->用户确认”
- 期望：
  - 仅出现一次 `create_company action=apply`
  - 不再出现 `action=draft` 与 `action=confirm`（且调用会报 schema/enum 不支持）
  - 创建成功后直接输出实例信息与实体列表

### 4.4 路径与调用次数验收
- 期望：
  - 不再出现“绝对路径被拒后再改相对路径”的往返；
  - 单次实体创建工具调用次数显著下降（目标 <= 3 次核心调用：必要时 `create_team` + `create_entity` + 可选一次补充）。

---

## 5. 风险与回滚

### 风险
- 自动补模型配置若优先级处理不当，可能覆盖用户期望。
- CEO 意图归一若规则过宽，可能误把“角色分析”当作“角色创建”。
- 强制单次 apply 后，若 payload 缺字段，可能导致一次调用失败率上升。
- 硬切换后，历史脚本/旧提示词若仍调用 `draft/confirm` 会立即失败。

### 缓解
- 仅在字段缺失时补齐，不覆盖已有值。
- 关键词归一后增加一次确认句（“你是要创建实体，还是做角色分析？”）作为兜底。
- 在调用 apply 前增加 payload 完整性检查（instance/ceo/entities/resource 四层字段）。
- 在发布说明中明确破坏性变更：`create_company` 只支持 `action=apply`。

### 回滚
- 若 P2/P3 出现偏差，可先保留 P1（模型可用性），回滚单次 apply 强约束与 CEO skill/SOP 扩展；
- 若必须回滚，需恢复 `draft/confirm` 分支与 schema 枚举（明确为代码回滚，不做运行时兼容）。

---

## 6. 非目标（本轮先不做）

- 不在 4.0 处理 admin 与 CEO 全量实体描述风格统一重构（你已标注后续优化）。
- 不在 4.0 引入跨实例消息总线完整实现（`assign_task` 仍按现阶段路线）。

---

## 7. 建议的实施顺序（你确认后执行）

1. 先做 P1（模型配置补齐 + 测试）  
2. 再做 P2（CEO skill + 提示词）  
3. 最后做 P3（`create_entity` 参数扩展）  

这样可以先把“CEO不能对话”这类阻塞问题彻底消掉，再收敛创建体验。
